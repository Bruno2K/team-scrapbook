## When to create an ADR

Create one when a decision has durable consequences and at least one of these applies:

- it changes architectural boundaries or durable contracts;
- it selects infrastructure or platform strategy;
- it establishes significant consistency, delivery, or security semantics;
- it has meaningful alternatives/tradeoffs; or
- rediscovering the decision later would be expensive or confusing.

Do not create one for ordinary implementation details, trivial refactors, routine dependency updates, temporary debugging choices, or decisions already fully dictated by an existing ADR or Spec. Link the governing record instead. Do not create retroactive ADRs unless an owning issue requires them.
